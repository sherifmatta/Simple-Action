Simple Action — key states

Every non-resting state of the single screen, each as its own labelled panel. Static mock: nothing here responds to interaction. Tokens are Lavender Mist (variation 4) plus the Finalize additions — border-control #8C8BAC on every component boundary, accent-deep on the checked box of a completed row, and the clay danger ramp on the one banner region.

Load failure and save failure are separate states with separate words (E1, E2), and add failure is a third with its own recovery (E3).

Input populated The add was optimistic: pay water bill appeared at the top of the list the moment it was submitted. The save failed, so it has been removed from the list and its text has been returned to the input — shown here populated, not empty. Nothing the user typed is lost, and the counts have gone back to 4 / 2 / 2.

Three recoveries, one region: load re-requests, toggle and delete restore the row, add restores the text. Add failure has its own string — Couldn’t add that Todo. — and never borrows the save-failure wording in E2. An add is not a change to something that exists; it is a thing that failed to come into being, and the user is looking at their own text back in the input, not at a row that reverted. Four error kinds, three strings: load, add, and one shared by toggle and delete, which share a shape.

Rendered at phone width (362px card) on purpose: this is the check the memlog called for — Poppins' wide round forms against long Todo text on a narrow column. At 14.5px the text stays legible, wraps, and never forces the page sideways.

The counter is a bare numeral — 38, no unit and no label. Not "38 left", not "462/500": no new word enters the interface. It holds text-muted #5A5A75 throughout and never takes the danger ramp, because it is not an error and reports none. There is no appearance change at exactly 500 — the count simply reaches 0 and keystrokes stop.

The ceiling is 500 characters. The remaining count is absent below ~450 and fades in past it, so the hard stop at 500 is never mysterious. Whether the input grows to fit (as drawn here) or caps its height and scrolls internally is not decided — see open question 3.

Ring is box-shadow: 0 0 0 1px #2680EB, 0 0 0 5px rgba(38,128,235,.30) — a 1px accent edge plus a 4px bloom — on the white card, on a white row and on every control not sitting on mint. It never changes the size of the element it surrounds. Every interactive target keeps a 44px minimum hit area even where the painted control is smaller.

The ring steps down on mint. #2680EB on row-complete #C3E9D7 is 2.97:1 — the identical failure that moved the checked checkbox — and a focus indicator is a non-text graphic identifying a control, so 1.4.11 applies to it too. The bloom does not rescue it: at 30% opacity it is fainter than the edge that already fails. On a completed row the ring is box-shadow: 0 0 0 1px #1B65C2, 0 0 0 5px rgba(27,101,194,.30) — 4.33:1. Same geometry, same blur, same opacity; only the hue value changes, so focus never reads as two different things. The second row in G3 is drawn with it.

Both boundaries in G3 are on the 1.4.11 floor: the unchecked box is border-control #8C8BAC at 3.28:1 on white, and the checked box on the completed row is accent-deep #1B65C2 at 4.33:1 on mint. On an active row the checked fill and the ring both stay #2680EB on white.
