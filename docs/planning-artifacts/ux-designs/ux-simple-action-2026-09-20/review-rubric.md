# Spine Pair Review — Simple Action

## Overall verdict

This pair is unusually disciplined on the things that normally break a spine: vocabulary is locked and never drifts ("Done" appears only as the banned term), the ten component names match exactly across four sections of two files, every `{path.to.token}` reference resolves, and all twelve contrast ratios stated in `DESIGN.md` are arithmetically correct — I recomputed each one. Where it fails the central question is provenance and recovery: all four rendered key screens in `.working/` are orphans, neither spine states the spines-win-on-conflict rule, and both still describe the palette as import-anchored after `.memlog.md` corrected that claim twice. Underneath that, three load-bearing behaviours are uncommitted — what `Retry` retries after a failed toggle/delete/add, what happens to a failed optimistic add's typed text, and the anatomy of the empty state that owns three of the product's designed states.

A consumer can source-extract the colour system, the typography ramp, the ten components and the four journeys cleanly. A consumer cannot build the empty state, cannot build error recovery, and has no way to discover that four key screens already answered questions the spine still marks unresolved.

- **medium** SM-2's coverage claim is only half met. prd.md:192 requires the list be identical "after reload **and after a browser restart**, every time", and FR-6's consequences add "a different browser or device sees a different, independent Todo List". ## 2. Token completeness — adequate

Extracted 18 colour tokens, 10 typography roles, 4 radii, 16 spacing tokens, 10 component objects from `DESIGN.md` frontmatter, plus every `{...}` reference in the prose of both files. **Every colour token carries a hex. Every reference resolves** — `colors.*`, `typography.*`, `rounded.*`, `spacing.*`, `components.todo-row-active`, `components.input-add`, `components.char-counter.appears-at`, `components.char-counter.ceiling`, `components.skeleton-row.pulse-duration`, and `{spacing.margin-phone}` in EXPERIENCE.md:160. `EXPERIENCE.md` contains no hex value, exactly as its header (line 13) promises. I recomputed all twelve stated contrast ratios (DESIGN.md:225–235, 346); **all twelve are correct to two decimals**, including the 4.69:1 tightest pair.

### Findings

- **high** Two non-text pairs fail the 3:1 floor that `EXPERIENCE.md:130` asserts is universally met ("every non-text graphic clears 3:1"). `{colors.accent}` `#2680EB` on `{colors.row-complete}` `#C3E9D7` measures **2.97:1** — that is the checked checkbox against a Completed row, specified at DESIGN.md:314 (`checked-background` / `checked-border` both `{colors.accent}`) and DESIGN.md:312. `{colors.hairline}` `#E3E2F0` on white measures **1.28:1** — that is the *unchecked* checkbox border and the input border (DESIGN.md:232, :314, :316), i.e. the only boundary identifying those controls (WCAG 1.4.11). Neither appears in the contrast block at DESIGN.md:346, which presents itself as exhaustive ("Every other text pair in the system has room"). The design's three-redundant-cue rule means this is not a comprehension failure, but it is an audit failure against a claim both spines make. *Fix:* add both pairs to the DESIGN.md contrast block with their real ratios; either darken the checked-checkbox border on mint to clear 3:1, or state explicitly that the checkmark glyph (3.91:1 on accent) plus the row fill carry identification and the 1.4.11 exception is taken knowingly. Soften EXPERIENCE.md:130 to match.

- **high** `danger-fill` is missing. `.memlog.md` bullet 43 is explicit: "Derived token needed: danger-fill. key-delete.html uses danger-text #8E3B22 as a FILL with a white label (~5.8:1)… DESIGN.md must name danger-fill explicitly rather than leaving the reuse implicit." No such token exists. Instead `DESIGN.md` specifies the opposite treatment: `delete-action.revealed-background: '{colors.danger-bg}'` (pale clay, line 196) and `dialog-delete.confirm-background: '{colors.danger-bg}'` (line 174). `.working/key-delete.html:232` and `:271` render both surfaces as solid `#8E3B22` with white labels (7.50:1 by my calculation, not 5.8:1). The last decision before Finalize did not land, the mockup that contradicts it is unlinked, and nothing tells a downstream consumer which destructive treatment is real. *Fix:* pick one. If the pale treatment wins, say so and note the mockup is superseded; if the filled treatment wins, add `danger-fill: '#8E3B22'` and repoint `revealed-background` and `confirm-background`.

- **medium** The `Enter` hint has no tokens. DESIGN.md:316 specifies "A small pill-outlined `Enter` hint sits at the trailing edge on pointer-width viewports", and EXPERIENCE.md:161 repeats it, but the `input-add` component object (lines 129–139) has no entry for it — no border colour, no label colour, no typography role, no radius. *Fix:* add `enter-hint-border` / `enter-hint-text` / `enter-hint-typography` to `input-add`, or drop the hint.

- **low** Spacing tokens are internally inconsistent. `card-padding-block: 20px` is not on the scale the prose states ("4 / 6 / 9 / 12 / 14 / 18 / 22 / 32 px", DESIGN.md:264) and is referenced nowhere. `card-padding-inline: 18px` duplicates `gutter: 18px`, and the prose names `gutter` for the card's inline padding (DESIGN.md:264), leaving the other token dead. `{spacing.2}`, `{spacing.5}`, `{spacing.6}`, `{spacing.8}` are never referenced. *Fix:* delete `card-padding-block` / `card-padding-inline` or make the prose use them; a downstream implementer will otherwise pick arbitrarily between 18px and 20px for card padding.

## 3. Component coverage — adequate

Extracted every component name from both files. Ten components — `todo-row-active`, `todo-row-completed`, `checkbox`, `input-add`, `filter-tabs`, `error-banner`, `dialog-delete`, `skeleton-row`, `char-counter`, `delete-action` — each have a frontmatter object and a prose bullet in `DESIGN.md.Components`, and a row in `EXPERIENCE.md.Component Patterns`. **Names match exactly across all four locations**, spelling and casing included. Behavioural rules are real multi-clause rules, not one-word descriptions, in every row. That part is strong.

### Findings

- **high** There is no `empty-state` component in either spine, and it owns three of the product's designed states. `DESIGN.md` scatters its anatomy across four sections without ever assembling it: "the empty-state dashed edge" (line 232), "the empty-state line" in `{colors.text-muted}` (line 229), "the dashed empty-state panel" at `{rounded.md}` (line 300), "the small glyph ring in the completed empty state" (line 304), "the single completed-state glyph ring" (line 224). No frontmatter object, no Components bullet, no Component Patterns row. Undefined: dash width, panel padding, ring diameter, ring fill, glyph stroke. Worse, the fragments are wrong against `.working/key-states.html:280–292`, which renders a 1.5px dashed panel at `--r-row` with 30px/18px padding and a **40px `--row-complete` mint ring with a `--text-completed` glyph on all three empty views** — not just the Completed one — and **two text roles**, `.line` at 14px `text-primary` over `.sub` at 13px `text-muted`, not one muted line. The mint ring on the All and Active empties also contradicts DESIGN.md:224's "Mint means *Completed*, full stop." *Fix:* add an `empty-state` component to both spines with the mockup's anatomy, resolve whether the mint ring is permitted on non-Completed views, and correct the `text-muted` attribution at DESIGN.md:229.

- **medium** The card — the single container the whole product sits in — has no component entry. Its radius (DESIGN.md:301), shadow (line 286), padding (line 264) and behaviour on desktop (line 268) are prose-only, and the two tokens that would carry it (`card-padding-block`, `card-padding-inline`) are orphaned. `.working/key-main.html` renders it at `padding:18px 16px 22px` phone / `22px 22px 26px` desktop — matching neither token. *Fix:* add a `card` component object, or fold card padding into the layout prose and delete the dead tokens.

- **medium** The empty-state copy is split in the mockup but joined in the spine. `EXPERIENCE.md:49` and the State Patterns row at :89 present `Nothing here yet. Type above to add your first Todo.` as a single string; `.working/key-states.html:371–372` renders it as a headline plus a sub-line at different sizes and colours. The Voice and Tone table is introduced as "Every user-facing string in the product" (line 44), so a consumer will build one paragraph. *Fix:* split the row into headline and sub, or state that the single string is deliberate and supersedes the mockup.

## 4. State coverage — adequate

Walked both IA surfaces. Covered and specified: initial load, empty ×3, load failure, optimistic add, optimistic toggle, optimistic delete, toggle revert, delete restore, character ceiling approach and stop, whitespace-only submit, focus, the ~580ms departure transition (Interaction Primitives), the once-ever first-run nudge, and two `prefers-reduced-motion` variants. The dialog surface needs no load/empty/error state — delete is optimistic — and that is correctly implied.

### Findings

- **high** The load-failure string is wrong, and the correct one is missing. `EXPERIENCE.md:92` and the UJ-4 edge case at `:229` both show `Couldn't save that change.` for a *load* failure, where nothing was being saved. `.working/key-states.html:449` renders the load-failure banner as `Couldn't load your Todos.` and its copy header (line 49) lists it as a distinct product string. The Voice and Tone table (EXPERIENCE.md:52) has only the save string while claiming to be exhaustive. A consumer building from this spine will ship "Couldn't save that change." on a cold-start network failure. *Fix:* add `| Error banner — load failure | Couldn't load your Todos. + Retry |` to the string table and repoint EXPERIENCE.md:92 and :229.

- **high** Add-failure has no state row and no recovery path. Toggle and delete each get a dedicated revert row (`Toggle revert`, `Delete restore`, lines 95 and 97); add's failure is one clause inside the success row — "On failure, the row is removed and the banner reports it" (line 93). But the same row also specifies that a successful submit "clears the input", and the submit was optimistic, so on failure the user's typed text is gone from both the list and the input with nothing said about holding it. prd.md §5 requires that failures "never leave the interface stuck or silently wrong" and addendum §E requires errors be "recoverable in place". *Fix:* add an `Add revert` row stating explicitly whether the text is restored to the input, and if not, what `Retry` operates on.

- **high** `Retry` has defined semantics for exactly one of the four errors it owns. `EXPERIENCE.md:77` says the banner "Owns every error in the product: load failure, failed toggle, failed delete… Carries `Retry`. Dismisses when the retried operation succeeds or when the user performs a successful operation of the same kind." Only the load-failure Retry is then specified (line 92: "re-requests the Todo List and returns to the initial-load skeleton"). Undefined: what Retry does after a failed toggle (re-toggle which row, in which direction, when the row has already reverted?), after a failed delete (re-open the dialog, or delete silently?), after a failed add; and what happens when a second error arrives while the banner is already occupied. This is the single most-used control in the error path. *Fix:* give the `error-banner` Component Patterns row a four-line table of Retry behaviour per error kind, plus a rule for concurrent errors (replace / queue / coalesce).

- **medium** The add-during-load race is unspecified. State Patterns line 88 makes the input "already real and interactive — the user can start typing before the list arrives"; line 93 says a submitted Todo "appears at the top of the list immediately". If the list request has not resolved, the list region is showing skeletons. Whether the optimistic row renders over the skeletons, is queued, or is clobbered when the list response lands is undefined. *Fix:* one clause in the Initial load row.

- **low** The number of skeleton rows is unspecified in both spines. `.working/key-main.html`'s open-question block settles on three; the spine does not say. *Fix:* state a count or a rule ("three, or the last known list length").
